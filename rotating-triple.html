Rotating Triple-Sig: A better bunker?

An Algorand account type protected by Ed25519, Falcon-1024 and XMSS signatures. Each confirmed spend rotates authority to fresh Ed25519 and Falcon keys and a new range of XMSS leaves.

  1. Three keys on every transaction, not one

    Each of its transactions is protected by three keys from three unrelated families of cryptography. All three must sign. Even if two of those schemes were broken, the third would still protect the account.

    Falcon-1024 · latticeXMSS · hash-basedEd25519 · elliptic curve

  2. A new key set on every transaction

    Each confirmed spend rekeys the account to a new stage with fresh Ed25519 and Falcon-1024 keys and its own 64 XMSS leaves. One XMSS tree serves 1,024 stages, so its public root is shared. The account’s address, balance and assets never move.

  3. Invisible at rest

    The next stage’s program and its fresh Ed25519 and Falcon public keys stay off chain until it signs. Its authorizer address is a 32-byte hash. The shared XMSS root is already public once an earlier stage in that tree has signed.

  4. Visible only as it is retired

    The live stage’s program becomes visible when a transaction is submitted. Once that transaction is final, usually within about 3 seconds, the stage is retired: the same transaction has rotated in fresh Ed25519 and Falcon keys and a new XMSS leaf range. The next stage rejects signatures using the retired range.

  5. Three signature checks and a race

    A forged spend must pass all three signature checks and finalize before the real spend rotates authority away. Fresh Ed25519 and Falcon keys are exposed at broadcast; the shared XMSS root may have been public longer. Each stage can sign up to 64 distinct attempts on separate leaves without reusing a one-time key. Reusing a leaf weakens the XMSS protection until rotation, so the signer tracks attempts in release memory and its audit log.

  6. No stateful smart contract required

    Authorization uses Algorand's stateless Logic Signatures. Each keyset verification program is sent just-in-time with the transaction, without deploying a stateful application. Fewer moving parts to implement and audit.
